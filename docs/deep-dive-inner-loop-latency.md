# 深掘り(主軸): 修正サイクルの遅延を、実測の内訳から削る

CNDW 学生プロポーザルの技術的な深掘りの主軸。**発表の軸は「速くして、ユーザー体験を良くする」**。
ユースケース(母が、AI が作ったアプリを何度も直す)から、遅延の内訳を測り、インフラで削れる所を削る。

- 全体の筋: [`talk-story.md`](talk-story.md) / 現状の構成: [`architecture.md`](architecture.md)
- 安全・コスト側の設計(Release、Preview データ、容量の強制): [`deep-dive-preview-release.md`](deep-dive-preview-release.md)
  — この文書の主軸とは別に、**遅い道(決定したあと)を支える**位置づけ。

> **根拠の凡例**: ✅ 実測 / 📐 設計のみ / 🔜 これから(実験で確かめる)

## 0. 主張と指標

> **家族が「直して」と頼んでから、直った版を目で確かめられるまでの時間を、インフラで縮める。**
> 縮められるのは、LLM を除いた部分と、**「最初の変化が見える」までの体感の時間**。LLM そのものは縮められない。

「速さ」を 3 つの指標に分ける(1 つの数字で「速い」と言わない)。

| 指標 | 意味 | 利用者にとって |
|---|---|---|
| **TTFC**(Time To First visible Change) | 依頼してから、直った版の**最初の変化**が画面に見えるまで | 「動き出した」と分かる。待てるかどうかを決める |
| **TTVC**(Time To Verified Change) | 依頼してから、直った版が**検証まで済んで**、安心して使えるまで | 「もう大丈夫」と思える |
| **TTP**(Time To Production) | 承認して、家族みんなが使える本番に反映されるまで | **時間がかかってよい**(遅い道) |

速い道は TTFC と TTVC を縮める。TTP は縮めない(正しさを優先する)。

## 2. 現状のベースライン(✅ 実測)

Control Plane が記録している段階の遷移の時刻から、成功した全ての操作のウォーターフォールを組み立てた
(ホームクラスタ、Gemini `gemini-3.8-flash`、Stage 1 の構成)。

| アプリ | 種別 | 合計 | 準備 | Agent の作業 | テスト | 本番の起動 |
|---|---|---|---|---|---|---|
| 買い物リスト | 作成 | 156 s | 17 s | 129 s | 4 s | 6 s |
| 買い物リスト | 変更 | 70 s | 5 s | 57 s | 4 s | 4 s |
| 天気 | 作成 | 212 s | 9 s | 193 s | 6 s | 4 s |
| 天気 | 変更 | 82 s | 14 s | 58 s | 5 s | 6 s |
| 天気 | 変更 | 56 s | 5 s | 42 s | 4 s | 4 s |

- 「準備」= 依頼から Agent の最初の進捗まで(snapshot などの Job、Pod の起動、CLI の起動)。「テスト」= Agent の Job が完了するまでのテストと後処理。
- スタブ Agent で作った最初のアプリ(18 s)は LLM を使わないので除外。
- **変更の中央値(n=3): 70 s。Agent の作業が 81%、インフラ(準備 + テスト + 本番の起動)が 19%。**
- 準備が 14 s の 1 回は、**image が更新された直後**(取得の時間が乗った)。他は 5 s。→ 更新直後の cold start は 9 s ほどの追加。
- サンプルは小さい。**統計ではなくベースライン**として使う。

### 2.3 ML1 の結果(✅ n=10): 上の推定を実測で更新する

> §2 の表(n=3)と §2.1・§2.2(n=1)は**初期の観察**。5 種類の変更 × 2 回の計測(M-009)で、次のように更新する。
> 詳しい表と条件は [`measurements/log.md`](measurements/log.md) の M-009。

| 区間 | 中央値 | 合計に占める割合 |
|---|---|---|
| 依頼 → Agent 開始 | 5.3 s | 3% |
| **書き始めるまで**(p90 103 s、範囲 43〜225 s) | **63.9 s** | **40%** |
| 書く(最初 → 最後) | 49.5 s | 31% |
| 書いたあと | 24.3 s | 15% |
| コンテナ内のテスト | 2.0 s | 1% |
| 終了 → READY | 7.7 s | 5% |
| **合計**(p90 214 s、範囲 76〜333 s) | **159.4 s** | |

- **インフラ分は合計の 10%**(15.4 s)。**インフラを完璧にしても、合計はほぼ変わらない。**
  LLM の時間(書き始めるまで + 書く)が約 7 割。
- **ライブ Preview が変えるのは「待ち方」**: 最初の変化(TTFC)は中央値で **93.9 s 早い(42%)**。
  最後の変更が落ち着くまで(TTVC-live)は **33.0 s 早い(23%)**。
- **書き始めるまで(40%)が最大の塊で、ばらつきも最大**。10 回に 1 回は最初の変化まで 2 分以上かかる(最大 225 s)。
  → 次の調査は **X1(この時間の中身)**。
- 初期の観察(n=1)の「最初の変化は約 25 s」は、**この依頼では当てはまらなかった**(中央値 69 s)。書き始めるまでは、依頼の中身で大きく変わる。
- ⚠ TTFC は「最初のファイルが書かれた時刻」。複数ファイルの変更では途中の状態で、完成の確認は TTVC-live に近い。

### 2.1 Agent の作業の中身(✅ ただし 1 回の観察。→ §2.3 で更新)

直近の天気アプリの変更で、ファイルの更新時刻から、Agent がいつ書いたかを復元した(コンテナの開始から)。

| 時刻 | 起きていること |
|---|---|
| 0〜20 s | まだ何も書かない(CLI の起動、ファイルの読み込み、モデルの思考) |
| **20 s** | 最初の画面ファイルを書き換える(`index.html`) |
| 23〜29 s | `server.js` とテストを書き換える |
| 29〜44 s | 書き終えたあとの時間(**44 s の 34%**): Agent 自身の確認・テストの実行・まとめ |

```
今(Stage 1)   依頼 ├ 準備 ┤───── 書き始めるまで ─────┤ 書く ┤──── 書いたあと ────┤ テスト ┤ 本番の起動 ┤ 家族に見える
                   5s          ~20s                      9s         15s              4s         4s        ≈ 56〜70 s

ライブ Preview     依頼 ├ 準備 ┤───── 書き始めるまで ─────┤ ← 最初の変化がここで見える (TTFC ≈ 25 s)
                   5s          ~20s
```

### 2.2 見えてきた限界(上限の計算。n=3・n=1 の初期推定。→ §2.3 で更新)

- インフラ分(準備・テスト・本番の起動)は**変更の 19%**。**インフラを完璧にしても、合計は 70 s → 57 s(−19%)が上限**。
- 一方、TTFC は別。ライブ Preview なら最初の変化は ≈ **25 s**(準備 5 s + 書き始めるまで ~20 s)。**70 s → 25 s(−64%)**。
  ただし「~20 s で最初に書く」は **1 回の観察**。分布を取る必要がある。
- つまり、**インフラで劇的に変えられるのは、総時間ではなく TTFC と TTVC**。ここを主題にする。

## 3. 遅延の予算と、削る余地

| 区間 | 今(変更の中央値) | 削れる量(上限) | 手段 |
|---|---|---|---|
| 準備: snapshot の Job | ~3 s | ~3 s → 0 | 下書きを本番から分離し、snapshot を不要にする(L3) |
| 準備: Agent Pod の起動 | 1 s(通常)/ 9 s(image 更新直後) | ~1〜9 s | image のダイジェスト固定 + `IfNotPresent`、事前取得(L4)、常駐セッション(L5) |
| 書き始めるまで(CLI の起動 + 読み込み + 思考) | ~20 s | 不明 🔜 | 会話の引き継ぎ・文脈の縮小・軽いモデル(L5・L7・L8) |
| 書く | ~9 s | LLM 側 | (主にモデル) |
| 書いたあと | ~15 s | **見かけ上は 0 にできる** | 書き終えた時点で Preview を見せ、検証は並行(L2) |
| テスト(プラットフォーム側) | 4 s | 並行にする | 並行検証(L2) |
| 本番の起動(入れ替え) | 4〜7 s | 速い道から外す | 速い道は Pod を作り直さない(L1)。本番の入れ替えは承認時だけ |

## 4. 工夫(インフラ)

| # | 工夫 | k8s の部品 | 縮めるもの | 見込み(仮説 🔜) |
|---|---|---|---|---|
| L1 | **ライブ Preview**: Agent と Preview が同じ PVC を共有し、Preview は常駐して、ファイルの変更を即座に反映(`node --watch`) | PVC + `subPath` + `readOnly`、Deployment を維持 | TTFC。本番の入れ替え(4〜7 s) | TTFC ≈ 25 s(70 s から −64%)。反映は 0.5 s 以内(✅ 実験 X1) |
| L2 | **先に見せて、あとから検証**: 最後のファイルが書かれた時点で Preview を提示し、Agent の終了・テスト・画面確認は並行して「確認中」と表示 | 使い捨ての検証 Job を並行実行 | TTVC のうち「書いたあと」の ~15 s の体感 | 体感 −15 s 前後。**検証で問題が見つかったときの扱い**(取り消し・自動で直す)が設計課題 |
| L3 | **下書きを本番から分離**: Agent が触るのは `draft/` だけ。本番は `releases/<n>` を読む。snapshot が不要になる | `subPath`、Deployment | snapshot ~3 s、壊れた状態を家族が見る回数 | −3 s。**家族に壊れた状態を見せない**(E1) |
| L4 | **cold start の削減**: Agent の image をダイジェスト固定 + `IfNotPresent`、更新時は事前取得(DaemonSet) | `imagePullPolicy`、DaemonSet | image 更新直後の +9 s | 更新直後も 5 s |
| L5 | **常駐する Agent セッション**: 編集の間は Agent の Pod を残し(アイドルで 0 へ)、会話を引き継ぐ | Deployment + スケールダウン(KEDA など)、`--resume` 相当 | 書き始めるまで ~20 s の一部(CLI の起動 + 文脈の読み込み) | **不明**。まず内訳を測る |
| L6 | **対話の Pod を優先**: 重い作業が裏で走っても遅延が悪化しない | PriorityClass、QoS、CPU スロットリング | 負荷時の TTFC の悪化 | 悪化を抑える |
| L7 | **簡単な修正は軽いモデルへ** | (モデル側) | Agent の作業 | 不明 |
| L8 | **足場を用意**: テンプレート、プロジェクトの地図を Agent に渡し、探索のターンを減らす | AGENTS.md、事前生成のファイル | 書き始めるまで | 不明 |

**インフラとして深いのは L1・L2・L5・L6**(共有 volume、並行パイプライン、常駐とスケールゼロ、スケジューリング)。
L7・L8 は LLM 側の工夫で、効果を測って「インフラでは縮まらない部分」の正直な報告にする。

## 5. 測定の設計

**測る点(トレース)**

| 点 | 取り方 |
|---|---|
| 依頼を受けた時刻 | Control Plane(記録済み) |
| helper Job の開始・完了 | Job の status |
| Agent Pod の作成・コンテナの開始 | Pod の status(記録済み) |
| Agent の開始(entrypoint の最初) | entrypoint がタイムスタンプを出力(新規) |
| **最初のファイル書き込み**・最後の書き込み | `inotifywait` で `/workspace` を監視し、時刻を記録(新規。プラットフォームが書く `AGENTS.md` 等は除外) |
| Agent の終了、プラットフォーム側のテストの開始・終了 | entrypoint のタイムスタンプ(新規) |
| Runtime の Ready | Control Plane(記録済み) |
| 各ターンのトークンと時間 | Gemini CLI の `--output-format stream-json`(新規。LLM の内訳) |

出力は 1 行の `AAP_TRACE {json}` として Agent のログに残し、Control Plane が回収して Operation に保存する。
集計は `hack/latency-report.sh`(新規)で、分布(中央値と p90)を出す。

**ルール**
- 同じ依頼の集合(下の「ベンチマークの依頼」)を、構成を変えるたびに N 回(目安 10〜20)流す。
- LLM のばらつきが大きいので、**平均ではなく中央値と p90**。1 回の観察で言い切らない。
- 条件を記録する: モデル、image の更新直後か、ノードの負荷。
- 費用: 1 回の修正は数円〜数十円程度の見込み(🔜 実測)。回数と予算を先に決める。

**ベンチマークの依頼(案)**
- B1: 文字を大きくして(見た目だけの小さな変更)
- B2: ボタンの色を変えて、押したら少し動くようにして(見た目 + 少しの動き)
- B3: 入力欄を 1 つ増やして、保存されるようにして(データの形が変わる)
- B4: エラーの表示を分かりやすくして(複数ファイル)
- B5: くるくるが消えないバグを直して(実際に起きた不具合の再現)

| X4 | **L4 cold start** | image 更新直後の準備時間 | 準備の中央値 | 14 s → 5 s | 差がなければ不要 |

正直な内訳が出ること自体が、発表の価値になる。

## 8. リスクと未決事項

| 項目 | 内容 | 方針 |
|---|---|---|
| LLM のばらつき | 同じ依頼でも時間が大きく変わる。時間帯の影響も | 中央値と p90、回数を増やす |
| 費用 | 計測のたびに API を呼ぶ | 事前に回数と上限を決める。Google 側の予算も設定済みか確認 |
| ライブ Preview の危険 | Agent の途中の壊れたコードを Preview が実行して落ちる、再起動の連続 | 再起動の間引き、クラッシュ時に前の正常な版を表示、E11 で境界を測る |
| 並行検証で問題が出たとき | 先に見せた版を取り消すか、自動で直すか | 取り消しの UI と、自動の差し戻し(上限 N 回)を設計 |
| 常駐セッションの費用 | 待機中の Pod がメモリを使う(ワーカーは 5 GB) | アイドルでゼロへ。同時に常駐できる数に上限 |
| 速さだけを見て安全を落とす | 速い道は不完全でよいが、**本番には出さない** | 速い道と遅い道を分ける(§1)。Preview も NetworkPolicy・Data の分離は維持 |
| 主張の範囲 | 総時間の大半は LLM で、インフラでは縮まらない | 発表では「縮まらない部分は縮まらない」と言い、TTFC と TTVC を主張する |

## 9. 発表での位置づけ

> 第 3 幕の主題: **「内側のループは、最初の変化が見えるまでの時間で設計する」**。
> 総時間の 8 割は LLM でインフラでは縮まらない(✅)。縮められるのは、LLM を待つ間に家族が見ているもの。
> Agent と Preview が同じ volume を共有し、書いた瞬間に見える(L1)。検証は並行して回す(L2)。
> 決定したあとの Release、Data、容量の強制は、別の速度で、正しさのために設計する([`deep-dive-preview-release.md`](deep-dive-preview-release.md))。
