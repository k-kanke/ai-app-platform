## M-001 修正サイクルの遅延の内訳(トレースなし)

- **日時**: 2026-10-05(取得)。対象の操作は 2026-10-04〜05 に実施。
- **何を**: 成功した作成・変更の、依頼から READY までの内訳。
- **方法**: `hack/latency-report.py --ssh ubuntu-26 --save docs/measurements/data/baseline-2026-10-05.json`
  Control Plane が保存している段階の遷移の時刻(QUEUED → … → READY)と Operation から組み立て。
  再集計: `hack/latency-report.py --from docs/measurements/data/baseline-2026-10-05.json --exclude app-2ef57e`
- **環境**: ホームクラスタ(worker 4 CPU / 5.1 GB、Windows PC 上の VM)、Stage 1、Agent = Gemini CLI 0.62.0 + `gemini-3.8-flash`。
  `app-2ef57e` はスタブ Agent の作成のため除外。
- **結果**(秒):

| アプリ | 種別 | 依頼→Agent 開始 | プラットフォーム側のテスト | Job 完了→READY | 合計 |
|---|---|---|---|---|---|
| 買い物リスト | 作成 | 17.3 | 3.9 | 6.1 | 156.4 |
| 買い物リスト | 変更 | 5.4 | 4.0 | 4.1 | 70.3 |
| 天気 | 作成 | 9.3 | 6.1 | 4.1 | 212.5 |
| 天気 | 変更 | 13.9 | 4.6 | 6.1 | 82.2 |
| 天気 | 変更 | 5.3 | 4.5 | 4.1 | 56.2 |

  変更の中央値(n=3): **合計 70.3 s**(p90 79.8 s)。Agent が実行している区間(合計 − 上の 3 区間)は約 57 s で、**約 8 割**。
- **注意**: n が小さい。依頼→Agent 開始が 13.9 s の 1 回は、**image 更新の直後**(取得の時間が乗った)。
  この時点では Agent の内部(最初の書き込みなど)は取れていない → M-002、M-005 以降で補う。

## M-003 共有 PVC の挙動(kind の環境)

- **日時**: 2026-10-05
- **何を**: (a) 別 Pod の書き込みが、読み取り専用で mount した Pod の `node --watch` に届くまでの時間 (b) 読み取り専用の強制 (c) 10Mi の PVC に 100MB 書けるか
- **方法**: 検証用 kind クラスタ(`local-path`)に、同じ PVC を mount する Pod を 2 つ。書き込みは `kubectl exec`。(a) は `kubectl exec` の往復を含む壁時計時間。
- **結果**: (a) **0.5 s 以内**で再起動 (b) 読み取り専用の Pod は `Read-only file system` で拒否 (c) **100MB 書けた**(`local-path` は容量を強制しない)
- **注意**: n=1。(a) は `kubectl` の往復を含む上限の値で、実際はもっと短い。kind はホームクラスタとは別の環境。

## M-004 Release の方式比較・クォータ(storage ベンチマーク)

- **日時**: 2026-10-05
- **何を**: 作業ツリーの複製(Release 作成・ロールバック)の時間とディスク増加、データのクローン、容量の強制。
- **方法**: `hack/bench-storage.sh`(特権コンテナで、ループデバイス上の ext4 / XFS を比較)。各 5 回の中央値。
  出力: `docs/measurements/data/storage-bench-2026-10-05.txt`
- **環境**: Docker Desktop の Linux VM(カーネル 6.8、aarch64)。**実際のワーカーではない**。
- **結果**: [`deep-dive-preview-release.md`](../deep-dive-preview-release.md) §0.1 の表のとおり。要点:
  9,193 ファイル / 324 MiB — ext4 全コピー 1.07 s / +352.7 MiB、XFS reflink 0.22 s / +5.8 MiB。
  200 MiB のデータのクローン 9 ms / +0 MiB(別 PVC の間、同じ XFS)。XFS プロジェクトクォータは 10 MiB で強制、ext4 は強制されない。
- **注意**:
  - 最初の実行は**基準が誤っていた**(GNU `cp` が既定で reflink する)ため、`--reflink=never` に直して再実行した。誤った値は使わない(dev-log 参照)。
  - LVM thin と ext4 のプロジェクトクォータは、環境のカーネルの制約で**測れていない**。
  - **修正サイクルそのものは速くしない**(Release の作成と、データのクローンの話)。

## M-005 Agent の計測(トレース)の正しさの検証

- **日時**: 2026-10-05
- **何を**: `entrypoint.sh` のトレース(最初・最後の書き込み、Agent の開始・終了)が、既知のタイムラインと一致するか。
- **方法**: 書き込みの時刻が既知の擬似 Agent(+2.0 s に 1 つ目、+3.0 s に 2 つ目、+4.0 s に終了)を、Agent の image で実行。
- **環境**: Docker(Mac)、`aap-agent-runtime:trace`。
- **結果**: 最初の書き込み +2.01 s、最後 +3.02 s、終了 +4.02 s。**誤差 ±20 ms 以内**。失敗時にもトレースが出る(`rc:1`)ことも確認。
- **注意**: 計測の**正しさ**の検証であって、遅延の測定ではない。`writes` は inotify のイベント数(ファイル数ではない)。

## M-006 CI の所要時間(第 1 幕の根拠の代用)

- **日時**: 2026-10-05
- **何を**: コミットから image ができるまで(GitHub Actions)。第 1 幕「全部を Git に置く」の 1 回の修正に要する時間の代用。
- **方法**: `gh run list --repo k-kanke/ai-app-platform --limit 12 --json conclusion,createdAt,updatedAt`
- **結果**: 9 回の成功で **3分34秒〜4分46秒**(ほぼ 4 分)。push から Argo CD が拾うまでは別に約 3 分(作業中の観察で、**計測はしていない**)。

## M-007 実クラスタで初めてトレース付きの実行(動作確認の 1 回)

- **日時**: 2026-10-05 15:44〜15:47 JST(06:44〜06:47Z)
- **何を**: トレースが実クラスタで取得・保存されることの確認。同時に、最初のトレース付きの実測。
- **方法**: 使い捨てのアプリ(`trace-test`)を API で作成(依頼: 「ボタンが 1 つあって、押すと数字が 1 ずつ増える、とてもシンプルなページ」)。
  `hack/latency-report.py --ssh ubuntu-26 --since 2026-10-05T06:00:00Z --save docs/measurements/data/trace-verify-2026-10-05.json`
  終了後に `purge=true` で削除。
- **環境**: M-001 と同じ。Control Plane と Agent の image を**入れ替えた直後**(Agent の image は更新後の初回取得 = cold start を含む)。
- **結果**(依頼からの秒):

| 区間 | 値 |
|---|---|
| 依頼 → Agent 開始 | 18.5 |
| Agent 開始 → **最初の書き込み**(pre-write) | **51.5** |
| 書き込み(最初 → 最後) | 27.0 |
| 最後の書き込み → Agent 終了(post-write) | 20.5 |
| コンテナ内のプラットフォーム側のテスト | 0.6 |
| コンテナ終了 → READY | 10.4 |
| **TTFC**(最初の書き込みまで) | **70.0** |
| TTVC-live(最後の書き込み + 3 s) | 100.0 |
| **合計(家族が待つ時間)** | **128.5** |

  書き込みのイベントは 10 個。
- **観察**:
  1. **単純なページの作成でも、書き始めるまでに 51.5 s**かかった(M-002 の変更では約 20 s)。書き始める前の時間が大きく、**LLM 側の時間**。ここがインフラで縮まるかは未知(L5・L8、X1)。
  2. 書き終えたあと終了までが 20.5 s(合計の 16%)。ライブ Preview で書き終わりを検出して見せれば、体感で外せる(L2)。
  3. ライブ Preview なら、最初の変化は 70.0 s で見える。実際の合計 128.5 s より **58 s 早い(−45%)**(作成の場合)。
  4. **定義の違いに注意**: M-001 の「テスト」(4〜6 s)は、TESTING の通知から STARTING まで(コンテナ内のテスト + Job 完了を Control Plane が検知するまでの時間 + 終了処理)。
     トレースの「プラットフォーム側のテスト」(0.6 s)は**コンテナの中だけ**。残りの数秒は、コンテナの外の待ち(Job の完了検知など)で、「コンテナ終了 → READY」に含まれる。M-001 とトレース付きの値を直接比べない。
- **注意**: **n=1**。作成であって変更ではない。依頼が単純。image 更新直後の cold start を含む(依頼 → Agent 開始が 18.5 s と長い理由の一部)。ベースラインとしては使わず、動作確認の記録とする。
